# Design Note

1. **Categorization is a small rule engine, not a lookup map.** Vendor names are normalized: lower-cased, accents removed, and punctuation turned into spaces, so `SWIGGY*Order 88` becomes `swiggy order 88`. Rules are `EXACT` (the whole name must match) or `CONTAINS` (the rule's words must appear together as whole words inside the name). The most specific rule wins: an exact match first, then the CONTAINS pattern with the most words (ties go to the longer pattern). That way `uber eats` → Food beats `uber` → Transport, and `uber` never matches "Tuber Farms". If no rule matches, the expense goes to a default **Other** category.
2. **User intent beats rules.** Each expense stores a `category_source` of `RULE`, `MANUAL` or `DEFAULT`. When a user picks a category manually, they can also save it as a vendor rule ("remember this vendor"). "Re-apply rules" only changes expenses whose source is not `MANUAL`.
3. **Anomaly = amount > 3 × the average of the *other* expenses in the same category** (a leave-one-out average). If the expense were included in its own average, the outlier would hide itself. With 3 items, `x > 3·mean` is mathematically impossible. The check is done in exact decimal arithmetic (`x·(n−1) > 3·(sum−x)`), and an expense is only judged once its category has at least 2 other expenses.
4. **Flags are stored and recomputed on every write.** Adding one expense changes the average for its whole category, so older flags can change too. Every add, edit, delete, import or re-categorization recomputes the affected categories in the same transaction. A CSV import recomputes once per category, not once per row. Only the flag is stored; the baseline the UI shows to explain *why* ("22.6× the Shopping average of ₹1,899") is derived at read time from per-category count and sum, so a write only UPDATEs rows whose flag actually flipped.
5. **Data model:** `category`, `vendor_rule (pattern, match_type → category)` and `expense`. Amounts are `NUMERIC(12,2)` and `BigDecimal` (never floating point). Each expense keeps a `vendor_normalized` column used to group "top vendors", so "Swiggy" and "SWIGGY." count as one vendor. The schema is owned by Flyway migrations, with CHECK constraints and indexes on date, category, vendor and anomaly.
   **Query budget:** no endpoint issues per-row queries (verified by counting SQL). List and dashboard reads use fetch joins and aggregate queries, so they cost a fixed 4–7 queries whatever the page size. A 200-row CSV import reaches Postgres as a handful of statements, because expense ids come from a pooled sequence (IDENTITY would disable JDBC batching) and pgjdbc rewrites each batch into multi-row INSERTs.
6. **CSV import is forgiving per row and strict per file.** It follows RFC 4180 (the standard CSV format) and accepts header aliases, several date formats, and amounts written like `₹1,200`. Bad rows are reported with their line numbers and the valid rows are still saved. Re-uploading the same file is harmless because rows already in the database are skipped.
7. **Trade-offs and shortcuts:**
   - No authentication or multi-user support.
   - Recomputing a category is O(n) in Java. At scale I'd move it to a single SQL window-function `UPDATE`, or use the median/MAD (median absolute deviation) instead of the mean.
   - The rule cache lives in memory on one node.
   - Slash dates are read as DD/MM (Indian format).
   - Pure domain logic (rule engine, anomaly detector, CSV parser) is kept free of Spring so it can be unit-tested in isolation. Only that part has automated tests; the HTTP/database layer was tested by hand.
